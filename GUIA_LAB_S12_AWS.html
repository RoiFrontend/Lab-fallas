Laboratorio S12 (miércoles) · Rompe la arquitectura en AWS

AIS86 Arquitectura de Software · UNAMBA · Contenedor + réplicas + balanceador + orquestador, ahora en la nube · 100 min, en equipo
La idea de hoy. Es la misma imagen del lunes (lab-fallas:1.0) y son los mismos experimentos, pero en AWS. El lunes las piezas eran nginx, docker compose y kind. Hoy las reemplaza un servicio administrado:
  • el balanceador es un ALB;
  • el orquestador es ECS;
  • las máquinas las pone Fargate, y no ven ningún servidor.
Lo que se califica: los 3 puntos de control demostrados y explicados en el aula.

Del lunes a hoy: la misma pieza, otro nombre

0. Antes de clase (en casa: la verificación de la cuenta puede tardar)

  1. Una cuenta de AWS por equipo.
    • Un integrante entra a aws.amazon.com, elige crear una cuenta y se registra con su cuenta de Google o de GitHub. Es la nueva experiencia de AWS: la mayoría de las cuentas nuevas no necesita tarjeta y recibe hasta US$ 200 en créditos.
    • Luego invita a sus compañeros por correo desde AWS Settings. No compartan contraseñas.
  2. Anoten la región de su cuenta. A las cuentas con dirección de contacto en Perú, AWS les asigna US East (Ohio), us-east-2. Confírmenlo en AWS Settings → View all projects → Overview → Additional info → Region. Todo se crea en esa región; en la consola, revisen que arriba a la derecha diga esa misma región.
  3. Alarma de presupuesto, antes de crear nada. En la consola, entren a Billing and Cost Management → Budgets → Create budget → Use a template → Monthly cost budget, con un monto de US$ 10 y su correo.
  4. AWS CLI 2.32 o más reciente en la laptop de quien subirá la imagen: 
    aws --version
# si no está instalado o es más antiguo:
winget install Amazon.AWSCLI
  5. La imagen del lunes construida. docker images lab-fallas debe mostrar lab-fallas 1.0. Si no aparece, desde la carpeta lab-fallas: 
    docker build -t lab-fallas:1.0 ./app
    Las Mac con chip Apple (M1 a M4) construyen imágenes ARM por defecto, y Fargate usa x86 por defecto. En una Mac construyan así: docker build --platform linux/amd64 -t lab-fallas:1.0 ./app

Parte A · Subir la imagen a ECR (15 min)

A1. Iniciar sesión desde la terminal

aws login
# abre el navegador: elijan su sesión de la consola
aws sts get-caller-identity
Deben ver: un JSON con Account (12 dígitos) y Arn. Anoten el número de cuenta.
Por qué: aws login entrega credenciales temporales que la CLI renueva sola hasta por 12 horas. No hay claves guardadas en la laptop que alguien pueda robar.

A2. Crear el repositorio y subir la imagen

Definan dos variables. En PowerShell (si su región no es Ohio, cámbienla):

$REGION = "us-east-2"
$CUENTA = (aws sts get-caller-identity --query Account --output text)
$REPO   = "$CUENTA.dkr.ecr.$REGION.amazonaws.com/lab-fallas"
aws ecr create-repository --repository-name lab-fallas --region $REGION
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin "$CUENTA.dkr.ecr.$REGION.amazonaws.com"
docker tag lab-fallas:1.0 "${REPO}:1.0"
docker push "${REPO}:1.0"

En bash: REGION=us-east-2; CUENTA=$(aws sts get-caller-identity --query Account --output text); REPO=$CUENTA.dkr.ecr.$REGION.amazonaws.com/lab-fallas, y luego los mismos comandos con $REPO:1.0.

Deben ver: Login Succeeded y, al final del push, una línea con digest: sha256:…. En la consola, ECR → Repositories → lab-fallas muestra la etiqueta 1.0. Copien el URI de la imagen: lo van a necesitar.
Plan B, si aws login no funciona con su cuenta: suban la imagen a Docker Hub, que ya usaron el lunes, como repositorio público. ECS puede descargar de ahí sin credenciales. 
docker tag lab-fallas:1.0 <su-usuario>/lab-fallas:1.0
docker push <su-usuario>/lab-fallas:1.0
# URI de la imagen para ECS: docker.io/<su-usuario>/lab-fallas:1.0

Parte B · Desplegar: 2 copias detrás de un ALB (30 min)

Todo se hace en la consola web: console.aws.amazon.com/ecs/v2.

B1. Crear el clúster

Clusters → Create cluster → nombre lab-fallas. En Infrastructure dejen AWS Fargate (serverless), que es la opción por defecto → Create.

B2. Crear la definición de tarea

Task definitions → Create new task definition:

Campo Valor
Task definition family lab-fallas
Launch type AWS Fargate
Operating system/Architecture Linux/X86_64
CPU / Memory .25 vCPU / .5 GB (lo mínimo: más barato)
Task execution role Create new role. Es el permiso para descargar la imagen y escribir logs.
Container: Name / Image URI api / el URI de la Parte A
Port mappings Container port 8000, TCP, protocolo HTTP
Log collection Déjenla activada: los logs van a CloudWatch

B3. Crear el servicio con su balanceador

Entren al clúster lab-fallas → pestaña Services → Create:

Sección Qué poner
Task definition / Service name lab-fallas (última revisión) / api
Compute Launch type FARGATE
Desired tasks 2
Deployment failure detection Revisen que estén marcados Use the Amazon ECS deployment circuit breaker y Rollback on failures. Así vienen por defecto.
Networking VPC predeterminada, todas sus subredes.
Security group → Create a new security group, nombre lab-fallas-sg, con dos reglas de entrada:
• HTTP, puerto 80, origen Anywhere
• Custom TCP, puerto 8000, origen Anywhere
Public IP: ON
Load balancing Application Load Balancer → Create a new load balancer, nombre lab-fallas-alb.
Container api 8000:8000; listener en el puerto 80, HTTP.
Target group nuevo lab-fallas-tg, HTTP.
Deregistration delay: 10.
Health check path: /health

Presionen Create. El ALB tarda unos minutos en quedar activo.

Por qué la IP pública: sin NAT Gateway (que cobra por hora), una tarea de Fargate solo llega a internet para descargar la imagen si está en una subred pública y tiene IP pública.
Por qué abrimos el 8000 a todo internet: es un laboratorio y así lo simplificamos. En producción, el puerto 8000 solo acepta tráfico del security group del ALB, y las tareas van en subredes privadas.

B4. Health checks más rápidos (mientras esperan)

Los valores por defecto del ALB son revisar cada 30 s y exigir 5 respuestas sanas seguidas: una tarea nueva tardaría unos 2,5 min en recibir tráfico. Vamos a acortarlos.

En la consola de EC2 → Target Groups → lab-fallas-tg → pestaña Health checks → Edit:

  • Interval: 10 s
  • Healthy threshold: 2
  • Unhealthy threshold: 2
  • Timeout: 5 s

Guardar.

B5. Abrir el servicio y el monitor

EC2 → Load Balancers → lab-fallas-alb → copien el DNS name.

curl.exe http://<DNS-del-ALB>/
# levantar solo el monitor del lunes, desde la carpeta lab-fallas:
docker compose --profile monitor up -d monitor

Abran http://localhost:8090, peguen http://<DNS-del-ALB>/ en la caja de URL y presionen ▶ Iniciar.

Deben ver: cuadritos de 2 colores que se alternan. Es el ALB repartiendo con round robin, su algoritmo por defecto. En lab-fallas-tg → Targets, las 2 IP aparecen como healthy.
✅ PUNTO DE CONTROL 1. Muestren: la URL del ALB respondiendo en el monitor con 2 colores, y los 2 targets en estado healthy. Uno de ustedes, elegido al azar, explica qué pieza de AWS reemplaza a cada pieza del lunes.

Parte C · Romperlo en la nube (35 min)

C1. Matar una réplica

Predigan antes de ejecutar. El lunes, nginx con proxy_next_upstream no mostró ningún rojo y el Service de Kubernetes sí mostró algunos. ¿Qué hará el ALB? ¿Habrá rojos? ¿Cuántos segundos? ¿Quién levantará una copia nueva?

Con el monitor corriendo, presionen 💥 Tumbar una réplica. Luego miren ECS → servicio api → pestañas Tasks y Events.

Deben ver:
  • Un color desaparece. ECS detecta que la tarea se detuvo, la saca del grupo de destino y lanza una tarea nueva: en uno o dos minutos aparece un color nuevo, con el contador en cero.
  • Es probable que aparezcan algunos rojos durante unos segundos. El ALB no reenvía a otra réplica una petición que ya falló, como sí hacía nginx con proxy_next_upstream.
Por qué: el orquestador mantiene el estado deseado («2 tareas»). Nadie levanta nada a mano: es lo mismo que hizo Kubernetes en la Parte C del lunes, pero administrado por AWS.

C2. Una réplica lenta: cambiar el algoritmo del ALB

En el monitor elijan 8 peticiones simultáneas y presionen 🐢 Volver lenta una réplica. Esperen unos 30 s y miren la latencia por réplica y cuántas peticiones recibe cada una.

Predigan: con round robin, ¿qué fracción de las peticiones recibe la réplica lenta? ¿Y con least outstanding requests?

Cambien el algoritmo en EC2 → Target Groups → lab-fallas-tg → pestaña Attributes → Edit → Load balancing algorithm: Least outstanding requests → Save changes. Limpien el monitor y vuelvan a medir 30 s.

Deben ver: antes, la réplica lenta recibía más o menos la mitad de las peticiones (unos 2000 ms cada una). Después recibe muchas menos, porque el ALB prefiere a la que tiene menos peticiones en curso. Es el least_conn de nginx del lunes, ahora con un clic.

El ALB tiene 3 algoritmos: round robin (por defecto), least outstanding requests y weighted random. Hay uno activo a la vez por grupo de destino.

✅ PUNTO DE CONTROL 2. Muestren: (1) la captura de la pestaña Events donde ECS lanza la tarea de reemplazo; (2) las dos capturas del monitor, antes y después de cambiar el algoritmo, con el porcentaje de peticiones de la réplica lenta.

C3. Desplegar una versión rota

Predigan: si publican una versión cuyo /health responde error, ¿se cae el servicio? ¿Cuánto tarda AWS en darse cuenta? ¿Qué pasa al final?
  1. ECS → Task definitions → lab-fallas → seleccionen la última revisión → Create new revision → en el contenedor api, Environment variables → Add: ROMPER_HEALTH = 1 → Create.
  2. Clúster → servicio api → Update service → elijan la revisión nueva → Update.
  3. Dejen el monitor corriendo. Miren las pestañas Deployments y Events del servicio y los Targets del grupo de destino. Tarda entre 5 y 10 minutos: mientras tanto, observen la transición en la consola y el monitor.
Deben ver:
  • Las tareas nuevas arrancan, pero el ALB las marca unhealthy (/health responde 500) y ECS las reemplaza.
  • Al llegar a 3 fallas, el umbral mínimo del circuit breaker, el despliegue queda en FAILED y ECS hace rollback a la revisión anterior. Lo verán en Events y Deployments.
  • Durante todo ese tiempo el monitor no muestra rojos: las 2 tareas viejas siguieron atendiendo, porque ECS no retira las viejas hasta que las nuevas estén sanas.
Por qué: el health check es la puerta de entrada de cada versión nueva. Sin él, AWS habría reemplazado una versión que funciona por una que no funciona. Es el C7 del lunes (rollout undo), pero automático.
✅ PUNTO DE CONTROL 3. Muestren la captura del evento de rollback y el monitor sin rojos durante el despliegue roto. Uno de ustedes explica por qué el usuario no se enteró.

Parte D · Limpiar (10 min, obligatorio)

El ALB y las tareas cobran por hora aunque nadie los use. Si lo dejan encendido un mes, consume unos US$ 50 de sus créditos.
  1. ECS → clúster → servicio api → Delete service. Marquen Force delete si lo pide.
  2. EC2 → Load Balancers → lab-fallas-alb → Actions → Delete. Luego, EC2 → Target Groups → lab-fallas-tg → Delete.
  3. ECS → Clusters → lab-fallas → Delete cluster.
  4. Pueden dejar la imagen en ECR (guardarla cuesta centavos al mes) o borrarla en ECR → lab-fallas → Delete.
  5. En su laptop: docker compose --profile monitor down
  6. Comprueben: EC2 → Load Balancers debe estar vacío y ECS no debe tener tareas en ejecución.
