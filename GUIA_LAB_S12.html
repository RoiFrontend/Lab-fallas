Laboratorio S12 · Rompe la arquitectura

AIS86 Arquitectura de Software · UNAMBA · Contenedores, balanceo de carga, orquestador y clúster · 90 min, en equipo
La idea de hoy. No vamos a escribir mucho código: eso ya lo hace su agente de IA. Vamos a ver fallar una arquitectura y a ver qué pieza la salva.
  • Cada experimento sigue tres pasos: romper, observar en el monitor visual y explicar qué pieza lo resolvió.
  • Lo que se califica es la explicación con evidencia (capturas), no el código.

0. Preparación (antes de clase o en los primeros 10 min)

  1. Docker Desktop abierto. Comprueben con docker version: debe mostrar Client y Server.
  2. docker login con su cuenta gratuita de Docker Hub. El aula sale a internet por una sola IP, y Docker Hub limita las descargas anónimas por IP.
  3. Instalar kind (para la Parte C). kubectl ya viene con Docker Desktop: si kubectl version --client responde, no lo instalen. 
    winget install Kubernetes.kind
# solo si kubectl no responde:  winget install Kubernetes.kubectl
# cierren y vuelvan a abrir la terminal, luego:
kind version
kubectl version --client
    Si winget no existe en su Windows, descarguen kind desde la página oficial: kind.sigs.k8s.io → Quick Start → Installing From Release Binaries.
  4. La Parte C levanta 3 «máquinas» dentro de Docker: necesitan unos 4 GB de RAM libres. Si la laptop no alcanza, hagan la Parte C en la laptop más potente del equipo.
  5. Copiar la carpeta lab-fallas a su repositorio del equipo y abrir una terminal dentro de ella.
Qué hay en la carpeta:
  • app/: un servicio pequeño en Python con un Dockerfile de 6 pasos. Ábranlo y léanlo: cada paso está comentado.
  • compose.yaml: 3 réplicas + nginx + Redis.
  • nginx/: una configuración buena y una defectuosa.
  • monitor/: la página visual.
  • k8s/: el clúster y la app para Kubernetes.
Qué hace el servicio:
  • GET / responde qué réplica atendió y un contador.
  • GET /health es el chequeo de salud.
  • POST /crash mata el proceso.
  • POST /lento vuelve lenta (2 s) a la réplica que lo recibe.

Parte A · Un contenedor solo (15 min)

A1. Construir y ejecutar

docker build -t lab-fallas:1.0 ./app
docker run -d -p 8000:8000 --name solo lab-fallas:1.0

Abran http://localhost:8000 y recarguen varias veces.

Deben ver: siempre la misma replica y un contador que sube.

A2. Romperlo

curl.exe -X POST http://localhost:8000/crash
docker ps -a
Deben ver: curl responde Empty reply from server (el proceso murió antes de contestar), el contenedor aparece en estado Exited (1) y el navegador ya no responde.
Por qué: una sola copia es un punto único de falla.

A3. Política de reinicio

docker rm solo
docker run -d -p 8000:8000 --restart unless-stopped --name solo lab-fallas:1.0
curl.exe -X POST http://localhost:8000/crash
docker ps
Deben ver:
  • el contenedor vuelve solo en unos segundos;
  • pero el contador empezó de cero.
Por qué: lo que vive en memoria del contenedor muere con él. Reiniciar no es lo mismo que no perder datos.
docker rm -f solo

Parte B · Réplicas y balanceador (30 min)

B1. Tres réplicas detrás de nginx

docker compose up -d --build
docker compose ps

Abran el monitor en http://localhost:8080 y presionen ▶ Iniciar.

Deben ver: cuadritos de 3 colores alternándose. Es nginx repartiendo en round robin.

B2. Matar una réplica: balanceador bien configurado vs. defectuoso

(a) Con la configuración buena. Con el monitor corriendo:

docker kill lab-fallas-api-2
Deben ver: ese color desaparece y no hay cuadritos rojos. nginx reintentó en otra réplica (proxy_next_upstream) y la marcó como caída (max_fails).

(b) Con la configuración defectuosa. Primero levanten de nuevo la réplica y cambien de configuración, con las 3 vivas:

docker start lab-fallas-api-2
# PowerShell:
$env:NGINX_CONF="nginx-defectuoso.conf"; docker compose up -d lb
# bash: NGINX_CONF=nginx-defectuoso.conf docker compose up -d lb

Limpien el monitor, inícienlo y vuelvan a matar la réplica:

docker kill lab-fallas-api-2
Deben ver: rojos constantes, más o menos 1 de cada 3 (error 504: nginx esperó 1 s a una réplica que ya no existe). Es el usuario recibiendo errores.

Comparen nginx/nginx.conf con nginx/nginx-defectuoso.conf: ¿qué dos líneas cambian?

Al terminar, restauren todo:

# PowerShell:
Remove-Item Env:NGINX_CONF; docker start lab-fallas-api-2; docker compose up -d --force-recreate lb
# bash: unset NGINX_CONF; docker start lab-fallas-api-2; docker compose up -d --force-recreate lb
Observación de arquitectura:
  • nginx averigua las IPs de las réplicas (api) al arrancar.
  • Si una réplica vuelve con otra IP, nginx no se entera hasta que se reinicia. Por eso recreamos lb.
  • Ese es el problema del descubrimiento de servicios, que un orquestador resuelve solo (Parte C).

B3. El defecto del estado en memoria

Miren la columna Último contador del monitor: cada réplica tiene su propio contador.

Por qué importa: si el contador fuera un carrito de compras, el usuario lo vería aparecer y desaparecer según la réplica que le toque.

Arréglenlo moviendo el estado fuera del contenedor, a Redis:

# PowerShell:
$env:REDIS_URL="redis://redis:6379/0"; docker compose up -d api
# bash: REDIS_URL=redis://redis:6379/0 docker compose up -d api
docker compose restart lb
Deben ver: un solo contador que sube de forma continua, sin importar la réplica, con la indicación «redis (compartido)».

B4. Una réplica lenta: round robin vs. menos conexiones

  1. En el monitor elijan 8 peticiones simultáneas y presionen 🐢 Volver lenta una réplica.
  2. Miren la latencia promedio: una réplica tarda unos 2000 ms, y aun así recibe 1/3 de las peticiones.
  3. En nginx/nginx.conf quiten el # de la línea # least_conn;, guarden y luego ejecuten: 
    docker compose up -d --force-recreate lb
    (Se recrea el contenedor para asegurar que lea el archivo editado.)
Deben ver: la réplica lenta recibe muchas menos peticiones. El balanceador la evita sin que nadie se lo diga.

Al terminar:

docker compose down

Parte C · Orquestador y clúster con Kubernetes (35 min)

C1. Crear un clúster de 3 nodos en su laptop

kind create cluster --config k8s/kind-cluster.yaml
kubectl get nodes
docker ps
Deben ver: 3 nodos: ais86-control-plane, ais86-worker y ais86-worker2. En docker ps, cada nodo es un contenedor que simula una máquina.
La primera vez descarga una imagen grande y tarda unos minutos. Háganlo apenas lleguen.

C2. Declarar el estado deseado

kind load docker-image lab-fallas:1.0 --name ais86
kubectl apply -f k8s/app.yaml
kubectl get pods -o wide

Levanten solo el monitor (la API ahora la sirve Kubernetes):

docker compose --profile monitor up -d monitor

Abran http://localhost:8090. Verifiquen que la caja de URL diga http://localhost:30080/ y presionen ▶ Iniciar.

No abran index.html con doble clic: el navegador puede bloquear las peticiones desde un archivo local hacia localhost.
Deben ver: 3 colores, pero en orden aleatorio, no alternados como con nginx: el Service de Kubernetes elige un pod al azar por cada conexión. La columna NODE de kubectl get pods -o wide dice en qué máquina quedó cada pod.
Lean k8s/app.yaml:
  • replicas: 3 es el estado deseado;
  • readinessProbe y livenessProbe son los health checks;
  • el Service encuentra los pods por la etiqueta app: api, no por IP. Eso es el descubrimiento de servicios.

C3. Borrar un pod

Abran una segunda terminal con kubectl get pods -w. En la primera:

kubectl get pods
kubectl delete pod <nombre-de-un-pod>
Deben ver: el orquestador crea otro pod al instante, con otro nombre y otra IP. El monitor apenas lo nota: como mucho, algún rojo aislado mientras el pod se apaga.
Comparen con la Parte B: ahí nadie levantaba la réplica muerta.

C4. Que se caiga el proceso

En el monitor, presionen 💥 Tumbar una réplica. Luego:

kubectl get pods
Deben ver: en un pod, la columna RESTARTS sube a 1: Kubernetes reinició el contenedor solo. Es probable que aparezcan algunos rojos durante unos segundos.
Por qué hay rojos aquí y no en B2(a): el Service de Kubernetes es un balanceador de capa 4 y no reintenta una petición fallida; nginx (capa 7, con proxy_next_upstream) sí lo hacía. Kubernetes saca al pod caído del reparto apenas detecta la caída, pero las peticiones que ya iban hacia él fallan. Por eso en producción se pone un balanceador de capa 7 (Ingress / Gateway) delante.

C5. Escalar

kubectl scale deployment api --replicas=5
kubectl get pods -o wide
Deben ver: aparecen 2 colores nuevos en el monitor, sin tocar ninguna configuración del balanceador.

C6. Que se caiga una máquina entera

docker stop ais86-worker
kubectl get nodes        # repitan cada 15 s
kubectl get pods -o wide # repitan cada 15 s
Deben ver:
  • mientras el plano de control todavía no se da cuenta, el monitor muestra rojos: el Service sigue enviando tráfico a los pods del nodo apagado;
  • en 1–2 minutos el nodo pasa a NotReady y los rojos desaparecen;
  • unos 15 s después sus pods se recrean en el otro worker. Los pods viejos quedan como Terminating: Kubernetes no puede confirmar su borrado porque la máquina no contesta. Es normal.
Eso es un clúster: perder una máquina no tumba el servicio, pero detectarlo toma tiempo, y ese tiempo es una decisión de diseño.
docker start ais86-worker
kubectl get nodes        # en 1–2 min debería volver a Ready
Si el nodo no vuelve a Ready en 2 minutos, no importa: sigan con C7. Al final se borra todo el clúster.

C7. Desplegar una versión rota

Primero vuelvan a 3 réplicas (así el resultado es más claro). Luego simulen que publican una versión cuyo chequeo de salud falla:

kubectl scale deployment api --replicas=3
kubectl set env deployment/api ROMPER_HEALTH=1
kubectl get pods                         # repitan cada 10 s
kubectl rollout status deployment/api   # se queda esperando: Ctrl+C
Deben ver:
  • un pod nuevo que nunca llega a 1/1 READY, y su RESTARTS sube (también falla el liveness);
  • los 3 pods viejos siguen atendiendo, y el monitor sigue sin rojos.
Kubernetes no reemplaza lo que funciona por algo que no pasa su health check. Con 3 réplicas, la estrategia por defecto (maxSurge 25 %, maxUnavailable 25 %) permite crear 1 pod extra y no retirar ninguno viejo hasta que el nuevo esté listo.

Vuelvan atrás:

kubectl rollout undo deployment/api

C8. Limpiar (importante: libera memoria)

kind delete cluster --name ais86
docker compose --profile monitor down
Detalle para los curiosos:
  • el Service de Kubernetes reparte por conexión (capa 4), mientras que nginx reparte por petición (capa 7);
  • el servicio del lab cierra la conexión en cada respuesta para que vean el reparto;
  • ¿qué pasaría si no lo hiciera?

Anexo · Ficha de consulta: balanceo de carga

1. Por qué existe

  • Escalado vertical (scale up): más CPU/RAM a un solo servidor. Tiene límite físico y sigue siendo un punto único de falla (SPOF).
  • Escalado horizontal (scale out): más copias en paralelo. Exige servicios sin estado y un balanceador que reparta.

2. Tipos de balanceador

CriterioTipoQué esEjemplos
ImplementaciónSoftwarePrograma en servidores comunes, VMs o contenedores. Barato y flexible; tú lo operas.NGINX, HAProxy, Envoy, Traefik
HardwareEquipo dedicado con chips especializados (p. ej. cifrado TLS) para tráfico masivo en centros de datos propios.F5 BIG-IP, NetScaler (antes Citrix ADC)
Nube (gestionado)Lo opera el proveedor; escala solo y trae health checks. En AWS incluye protección DDoS básica (Shield Standard).AWS ELB (ALB, NLB, GWLB), Azure Load Balancer (capa 4) / Application Gateway (capa 7), Google Cloud Load Balancing
Capa OSICapa 4 (transporte)Decide por IP, puerto y protocolo (TCP/UDP), una vez por conexión. Muy baja latencia; sirve para cualquier protocolo. No ve URL ni cookies.AWS NLB, HAProxy en modo TCP, Service de Kubernetes
Capa 7 (aplicación)Lee HTTP (método, URL, cabeceras, cookies) y decide en cada petición: /api/pagos a un servicio, /api/usuarios a otro. Puede reintentar y terminar TLS.nginx, AWS ALB, Envoy, Traefik, Ingress / Gateway API
AlcanceLocalEntre servidores de un mismo centro de datos o región.nginx, ALB en una región
Global (GSLB)Envía a cada usuario a la región más cercana o sana, con DNS inteligente o Anycast.Route 53, AWS Global Accelerator, Cloudflare

3. Algoritmos

AlgoritmoCómo decideÚsalo cuando…Dónde
Round robinEn orden: A → B → C → AServidores iguales, peticiones parecidasnginx y AWS ALB (por defecto)
Round robin ponderadoEn orden, según un pesoServidores de distinta capacidadnginx weight=, HAProxy
Menos conexionesAl que tiene menos peticiones en cursoDuración variable: pagos, descargas, WebSocketsnginx least_conn, HAProxy leastconn, ALB «least outstanding requests»
Menos conexiones ponderadoConexiones ÷ pesoServidores distintos y duración impredeciblenginx y HAProxy (respetan el peso)
Menor tiempo de respuestaAl más rápido (y menos cargado)La latencia es críticaNGINX Plus least_time (comercial), F5
Aleatorio / «dos al azar»Al azar, o elige 2 al azar y manda al menos cargadoMuchos balanceadores sin estado compartidoEnvoy, nginx random two, Service de Kubernetes (azar por conexión)
Hash de IPMisma IP de cliente → mismo servidorAfinidad de sesión sin almacenamiento compartido. Ojo: detrás de NAT (un aula entera sale con 1 IP) todos caen en el mismo servidornginx ip_hash; AWS NLB usa hash de flujo
Hash consistenteAnillo de hash: si entra o sale un nodo, solo se reasigna una fracción pequeñaCachés y sistemas que crecen o se achicannginx hash … consistent, Envoy
GeográficoSegún la ubicación derivada de la IPServicios en varias regionesRoute 53, CDNs

4. Términos relacionados

TérminoDefinición breve
Proxy directo (forward)Actúa en nombre de los clientes y los oculta ante internet (p. ej. el proxy de una red corporativa).
Proxy inverso (reverse)Se ubica delante de los servidores y oculta sus IPs; gestiona TLS, caché y balanceo. Todo balanceador de capa 7 es un proxy inverso. Algunos de capa 4 solo reenvían paquetes sin abrir la conexión (p. ej. IPVS en modo direct server return).
API GatewayProxy inverso de capa 7 que además centraliza autenticación, límite de peticiones (rate limiting), caché, transformación de cabeceras y métricas por API. El balanceador reparte entre copias de un servicio; el gateway decide a qué servicio va cada petición.
Health check activoEl balanceador consulta una ruta (p. ej. /health) cada N segundos. Tras X fallos seguidos marca al servidor como unhealthy y deja de enviarle tráfico; tras Y respuestas correctas lo reincorpora.
Health check pasivoDetecta fallas en el tráfico real (nginx max_fails). Algún usuario ya recibió el error.
Drenaje de conexionesAl retirar un servidor, deja terminar las peticiones en curso antes de apagarlo (en AWS: deregistration delay).
Sesiones pegajosas (sticky)Cookie o hash de IP que envía al usuario siempre al mismo servidor. Reparte peor y, si ese servidor cae, se pierde la sesión. Se evitan con sesiones sin estado (JWT) o estado compartido (Redis).
Terminación TLSEl balanceador descifra HTTPS (el certificado vive en él) y así puede leer la petición. La alternativa en capa 4 es TLS passthrough.
SPOFComponente único cuya caída detiene todo. Un balanceador sin redundancia también lo es.
VIP y activo-pasivoDos balanceadores comparten una IP virtual. El activo atiende y el pasivo vigila con latidos; si el activo cae, el pasivo toma la VIP en segundos (VRRP, p. ej. keepalived).
Activo-activoVarios balanceadores atienden a la vez; el tráfico se reparte entre ellos con DNS, ECMP o Anycast. Los balanceadores gestionados de la nube funcionan así y reemplazan sus nodos fallidos automáticamente.
Alta disponibilidad vs. tolerancia a fallosAlta disponibilidad: poco tiempo fuera de servicio (99,9 % ≈ 8,8 h al año). Tolerancia a fallos: seguir funcionando sin interrupción visible aunque un componente falle.
LatenciaCada salto agrega tiempo de ida y vuelta: un balanceador de capa 4 agrega menos que uno de capa 7.

5. En AWS (miércoles) y en Kubernetes

  • ALB (capa 7): web y APIs, reglas por ruta y dominio; algoritmos round robin (por defecto), least outstanding requests y weighted random.
  • NLB (capa 4): TCP/UDP/TLS, IP estática, latencia muy baja, hash de flujo.
  • GWLB (capa 3): para insertar firewalls o equipos de inspección.
  • CLB: generación anterior; no usar en proyectos nuevos.
  • Kubernetes: Service = capa 4. Ingress o Gateway API = capa 7. El controlador ingress-nginx se retiró en marzo de 2026 y lo recomendado ahora es Gateway API.
